# HPF taxonomy: C2PA mapping

**Working proposal. Mapping document version 0.9.** This is the version of this document, not of the HPF Standard. The example payloads use HPF Standard 0.9.4. The mapping is not part of the HPF Standard or of the C2PA specification.

> This mapping has not yet been submitted to the C2PA Technical Working Group. The intention is to raise it as an issue at [c2pa-org/specifications](https://github.com/c2pa-org/specifications). A link will be added here once it is open.

---

## Before reading this document

The `film.humanprovenance.ai-disclosure` assertion proposed here originates from a signed producer declaration, not from technical detection or tool-level processing. A C2PA manifest carrying this assertion is a technical record of a human declaration, not a machine-generated provenance signal. This distinction affects how the assertion should be created, signed, and interpreted. See [INTEGRATION.md](INTEGRATION.md) for implementation guidance.

A C2PA manifest contains cryptographically signed claims about an asset and its history. Signature validation checks the integrity of the signed claims and the signing credential; it does not establish that every claim is true. In C2PA terms, an ingredient is an asset used to create another asset. A finished film combines picture, sound, music and VFX from many sources, so provenance attached to one ingredient, such as a camera capture, does not by itself describe how the finished production was made.

C2PA does not determine whether a production is Assistive AI or Generative AI, and does not validate the producer's representation. HPF defines the semantic classification; C2PA is proposed only as a way to associate that classification with the asset and its provenance record. The assertion carries the result of the HPF declaration, not the full producer declaration or the reasoning used to reach the classification.

## Existing C2PA assertion types

This document was checked against C2PA 2.4. C2PA 2.5 was published in October 2026; it keeps the label rules, the action-level `digitalSourceType` field and the `c2pa.ai-disclosure` assertion described here, and section numbers below refer to 2.4.

C2PA 2.4 handles AI disclosure at the file and action level via the `c2pa.actions` assertion. Each action can include a `digitalSourceType` field drawn from IPTC's controlled vocabulary, which identifies how the asset was created or modified. The values most relevant to AI use are:

| IPTC digitalSourceType value | Meaning |
|---|---|
| `trainedAlgorithmicMedia` | The media was created algorithmically using an AI model trained on captured content |
| `compositeWithTrainedAlgorithmicMedia` | Existing media augmented or edited with a generative AI model, for example by inpainting or outpainting |
| `algorithmicallyEnhanced` | The media was modified or corrected by an algorithm without changing its main content, for example sharpening or noise reduction |

C2PA 2.4 also defines a standard assertion, `c2pa.ai-disclosure`, which carries model-level information about a generation step. That is different information from a production-level HPF classification, and neither replaces the other.

These values are IPTC NewsCodes. C2PA also maintains its own `digitalsourcetype` namespace for non-media data outputs, but for film assets the IPTC values apply.

Example action assertion for fully AI-generated content (C2PA 2.4):

```json
{
  "label": "c2pa.actions.v2",
  "data": {
    "actions": [
      {
        "action": "c2pa.created",
        "digitalSourceType": "http://cv.iptc.org/newscodes/digitalsourcetype/trainedAlgorithmicMedia",
        "softwareAgent": { "name": "<tool name>" }
      }
    ]
  }
}
```

Note: the placement of `digitalSourceType` within the action object may vary across C2PA implementations and spec versions. Treat this example as illustrative. Refer to the current C2PA specification rather than this document for authoritative field placement.

## Why existing assertions may not cover HPF

The `c2pa.actions` assertion describes what happened to a specific file at a specific point in its processing history. It is generated by the tool that created or modified the file, at the time of creation or modification.

HPF classification differs in two ways:

1. **Level of abstraction.** HPF classifies an entire production (a film or series), not an individual file. A single production may involve hundreds of individual assets, each with their own C2PA action history.

2. **Source of the assertion.** HPF classification is derived from a signed producer declaration, not from technical detection by the tool that processed the file. A platform receiving a finished film has no reliable way to reconstruct production-level AI use from file-level C2PA assertions alone.

Based on a review of C2PA 2.4, no existing C2PA assertion type appears to cover a production-level, declaration-based AI disclosure. The intention is to confirm this through engagement with the C2PA Technical Working Group.

## Proposed custom assertion

The C2PA specification supports third-party custom assertions using namespaced labels. HPF proposes the following:

**Label:** `film.humanprovenance.ai-disclosure`

This is a provisional working label. C2PA 2.4, section 6.2, requires an entity-specific namespace to begin with the entity's internet domain name, in the manner of Java package names (the specification's examples are `com.litware` and `net.fineartschool`), and allows hyphens and underscores after the first character of each namespace and label component. `film.humanprovenance.ai-disclosure` takes that form for the domain humanprovenance.film. The label has not been confirmed with the C2PA Technical Working Group. For any implementation before then, use `film.humanprovenance.ai-disclosure` and treat it as subject to change. Do not build stable production integrations against the label until it is confirmed.

**Payload:** the HPF record, matching [schema.json](schema.json), nested under a `data` key as part of the assertion structure. A record made under 0.9.3 or later carries three fields, including the released version the declaration covers. Records naming 0.9.2 do not require the released version and stay valid under the version they name.

```json
{
  "label": "film.humanprovenance.ai-disclosure",
  "data": {
    "hpf_standard_version": "0.9.4",
    "hpf_released_version": "Theatrical cut",
    "hpf_classification": "no_ai"
  }
}
```

The payload may include the optional `hpf_descriptors` array, exactly as an HPF record carries it. Its values are the descriptor vocabulary adopted in 0.9.4, and their meaning is tied to the version the record names. `altered_performance` may appear on an `assistive_ai` or a `generative_ai` record; every other value applies to `generative_ai` only; none applies to `no_ai`. More than one descriptor may apply:

```json
{
  "label": "film.humanprovenance.ai-disclosure",
  "data": {
    "hpf_standard_version": "0.9.4",
    "hpf_released_version": "Theatrical cut",
    "hpf_classification": "generative_ai",
    "hpf_descriptors": ["synthetic_performance", "generated_music"]
  }
}
```

Descriptors add factual context about the kind or kinds of AI output present; they do not determine the classification and carry no threshold. The array follows the rules in [schema.json](schema.json) and [INTEGRATION.md](INTEGRATION.md#descriptors): an assertion payload that carries descriptors is valid only if the same record would be valid outside C2PA. Those rules make the descriptors ready to implement in an HPF record. They do not change the status of this mapping, which remains a working proposal: the assertion label, its namespacing, and who signs it are still unsettled, and the warning below against production integration of the assertion still applies.

This assertion is placed in the `assertions` array of a C2PA claim, alongside any other assertions for the asset. It does not replace or conflict with `c2pa.actions` assertions; both may be present in the same claim.

`hpf_classification` must be one of the three values defined in [schema.json](schema.json). Treat schema.json as the authoritative source for the enum definitions.

`hpf_standard_version` takes the form `MAJOR.MINOR` or `MAJOR.MINOR.PATCH`, for example `0.9.4` or `1.0`. Read and validate a record under the version it names. Records made under 0.9.0 and 0.9.1 used an earlier version field; [INTEGRATION.md](INTEGRATION.md#records-made-under-earlier-versions) explains how they are kept. Treat the version as a string identifier, not a numeric version for comparison purposes. A major version increment (e.g. `0.x` to `1.0`) may indicate a change to the classification test or category definitions; implementations should flag assertions carrying an unrecognised major version for manual review rather than silently accepting or rejecting them. During v0.9 each revision carries its own patch number and may change requirements, so read a record under the version it names. Existing assertions are not invalidated by a version increment.

The value of `hpf_classification` maps loosely to IPTC `digitalSourceType` as follows:

| HPF classification | Nearest IPTC digitalSourceType | Fit |
|---|---|---|
| `no_ai` | None | No IPTC value corresponds. The absence of an AI-related action assertion does not establish `no_ai`; only a declaration does |
| `assistive_ai` | `algorithmicallyEnhanced` | Partial: IPTC value is per-asset; HPF value is per-production |
| `generative_ai` | `trainedAlgorithmicMedia` | Partial: same limitation |

The mapping is approximate. `hpf_classification` carries different semantics: it reflects a declared, production-level classification rather than a technical record of file-level tool use.

## Transcoding

Film files are transcoded multiple times across the distribution chain. Embedded C2PA manifests are often lost when files are transcoded. The recommended approach is Durable Content Credentials: the manifest is stored externally (as a sidecar file or in a manifest store) and bound to the asset via a hard binding (cryptographic hash of the asset content) plus one or more soft bindings (perceptual fingerprint or watermark) that allow the manifest to be rediscovered if it becomes separated from the asset. Soft bindings exist only to rediscover a separated manifest. They are not part of the HPF classification, carry no HPF semantics, and no specific watermark or fingerprint technology is required or endorsed.

See the C2PA specification's [External Manifests](https://spec.c2pa.org/specifications/specifications/2.4/specs/C2PA_Specification.html#_external_manifests) section for implementation details.

Because `hpf_classification` originates from a signed producer declaration rather than from a processing tool, the receiving platform does not need to create the assertion at the moment of file processing. It can be attached to an external manifest after the declaration is signed and the delivery is received. This fits the durable credential model.

Note that in the HPF flow, the receiving platform or distributor attaching the manifest is also responsible for computing and storing the hard binding against the received asset. This differs from most C2PA implementations, where the creating tool generates both the assertion and the binding at the point of file creation. Implementers should account for this when designing ingest pipelines. The C2PA spec supports multiple hash algorithms (SHA-256, SHA-384, SHA-512); implementers should agree on a hash algorithm with their distribution partners and apply it consistently to the same representation of the asset, typically the received master file before any platform-side transcoding.

## Trust and signing

C2PA signing uses an X.509 certificate. Validators that rely on the C2PA trust list treat a signer as trusted only where the certificate was issued by a Certificate Authority (CA) on that list. Who should sign the HPF Content Credential in a film distribution context is an open question that this proposal does not settle. The intention is to raise it as part of the C2PA Technical Working Group discussion.

The practical consequence of this open question: until a signing entity is defined and a certificate issued, standard C2PA validators will not treat the signer of a `film.humanprovenance.ai-disclosure` assertion as trusted. A trusted signature would still establish who signed the claims and that they have not changed, not that the classification is correct. Do not build production integrations against this assertion while this mapping is a working proposal. The payload is the HPF record defined in [schema.json](schema.json). The assertion label, its namespacing, its property names and who signs it are not settled, and the trust infrastructure is not in place.

## A note on the IPTC URL scheme

The `digitalSourceType` URL in the example assertion uses `http://cv.iptc.org/newscodes/digitalsourcetype/`. IPTC vocabulary URLs are used as identifiers rather than dereferenceable URLs; the `http` scheme is correct and matches the IPTC NewsCodes specification. Do not substitute `https`.

## Questions for C2PA Technical Working Group review

These are open questions to raise with the C2PA Technical Working Group. Nothing here has been reviewed or endorsed by C2PA; no technical endorsement is claimed until review is received.

1. Is a custom assertion the appropriate mechanism for a production-level disclosure of this kind, given that it is derived from a signed human declaration rather than tool-level processing?
2. Is a controlled descriptors array appropriate within the same assertion, or should type-of-content information be carried separately?
3. What namespacing, property naming, and versioning convention is preferred? In particular, do property names inside the `film.humanprovenance.ai-disclosure` namespace need the `hpf_` prefix, or is it redundant once namespaced? This is an open question for review, not a decision.
4. Should the assertion reference the authoritative external producer declaration, and if so, how?
5. For long-form film and television workflows where embedded manifests may not survive transcoding, is the proposed external or remote manifest, with the binding and recovery approach described above, appropriate?
